一、项目概述

1.1 项目定位

PharmaReg 是一个面向制药行业（GMP 药品生产质量管理规范 + GCP 药物临床试验质量管理规范）的 AI 合规知识问答平台。系统通过 RAG（检索增强生成）技术，将法规条款转化为向量索引，结合大语言模型实现条款级精准问答，同时提供偏差管理、变更控制、CAPA、SAE 上报、审计检查、培训考核等全套制药合规业务能力。

核心价值：法规条款精准检索与引用溯源 + 多角色 Agent 智能辅助 + 哈希链审计完整性 + 全链路幻觉防护。

3.2 RAG 11 步详解

1
意图分类 classify_intent(query)
关键词匹配 非LLM分类，基于硬编码关键词匹配区分三种场景： qa（常规问答，权重 doc:0.7/faq:0.2/case:0.1）、 faq_match（标准口径，权重 faq:0.6，触发词：口径/怎么办/如何处理/标准）、 deviation（案例查询，权重 case:0.6，触发词：案例/历史/发生过/之前）。
2
查询重写 rewrite_query(query, history)
① 历史上下文补充：多轮对话中将上一轮用户问题与当前问题拼接；② 缩写展开：GMP→药品生产质量管理规范、GCP→药物临床试验质量管理规范、ICH→人用药品注册技术国际协调会议。最多保留 2 条查询变体，控制检索次数。
3
多版本知识库获取 get_active_versions(db, tenant_id)
查询所有 status="active" 的 KbVersion 记录，按 activated_at 倒序。每个版本绑定独立的 doc/faq/case 三个 Milvus 集合，支持 GMP 2010 版与 GCP 2023 版等不同法规同时激活。
4
多通道向量检索 search_doc / search_faq / search_case
对每个查询变体 × 每个版本 × 每个通道分别做 Milvus 向量检索。 doc: top_k=40（法规条款），faq: top_k=10（标准口径），case: top_k=40（历史案例）。 检索时通过 filter=f"tenant_id == {tenant_id}" 做多租户隔离。
5
去重与预剪枝 _pre_prune_candidates()
跨 query/版本候选可达 50+ 条。先按 text[:100] 前缀去重，再按通道分组取向量分 top 8（每通道最多 8 条），控制 Rerank 输入规模避免超时。
6
CrossEncoder 重排序 reranker.rerank()
调用本地 bge-reranker-large 模型对所有候选逐对精排。 关键设计：top_n=len(doc_texts) 覆盖全部候选（而非 top_n=8），确保所有候选都有 rerank 分。
失败回退：rerank 调用失败时回退到向量余弦分排序，保证管线可用性。按 rerank_score 降序取 top 8。
7
FAQ 快速路径
如果 FAQ 候选的 rerank_score > 0.85，直接走 FAQ 标准口径路径，置信度固定 0.95，不再经过 LLM 生成和幻觉检测。mode="faq"。
8
上下文构建 + LLM 生成 build_context() → llm_client.chat()
将候选文本拼装为 [channel] text 格式上下文，配合 load_prompt("role_qa") 系统提示词送入 LLM。 Prompt 约束（role_qa.md）：只依据检索上下文作答、每个关键事实必须标注条款号、严禁编造、证据不足回答"未检索到依据"。
LLM 参数：temperature=0.3，同步重试 3 次（指数退避 2-10s），超时 60s。
9
幻觉防护 — 双重校验 hallucination.py
① 条款存在性验证 verify_clause_existence()：正则提取答案中的"第X条"，查 MySQL RegClause 表验证条款是否存在，计算 clause_hit_rate。
② 声明蕴含校验 verify_claims()：按句切分答案，仅对包含条款号或模态词（必须/应当/不得/禁止/要求/规定）的句子，用 LLM（temperature=0.0 保证确定性）逐句判定"是否有上下文依据"（yes/no）。
Stub 模式：verify_claims_stub() 用逐字匹配替代 LLM 裁判，关键词集多含"建议"。
10
置信度计算与阻断 compute_confidence() / should_block()
置信度公式：score = 0.5 × min(rerank_score, 1.0) + 0.3 × clause_hit_rate + 0.2 × claim_pass_rate
阻断规则：置信度 < 0.6 → 阻断；未验证声明占比 > 30% → 阻断；Stub 模式下 top_rerank < 0.45 → 阻断。 阻断后返回 mode="needs_human_review"。
11
引用溯源构建 build_citations()
根据 entity_id 回查 MySQL，构建 clause_id / clause_no / excerpt / collection 引用信息。doc 通道引用 RegClause 表，faq 通道引用 Faq 表。答案中每个关键事实可溯源到具体法规条款号与版本。

3.3 SSE 流式输出

rag_answer_stream() 通过 sse-starlette 实现 SSE 流式输出：

# 事件推送顺序
yield {"type": "citation", "citations": citations}     # ① 先推送引用信息
async for delta in llm_client.chat_stream(messages):  # ② 逐 token 流式
    yield {"type": "delta", "content": delta}
yield {"type": "done", "confidence": confidence}      # ③ 推送最终置信度
# 或阻断时
yield {"type": "flag", "flag": "needs_human_review"}  # ④ 推送阻断标记
yield {"type": "done", "confidence": conf, "mode": "needs_human_review"}
# 或异常
yield {"type": "error", "code": "INTERNAL"}            # ⑤ 推送错误码

Stub 模式下模拟流式：将拼接好的答案按 40 字符分块逐段 yield，前端体验与真实流式一致。

3.4 Stub 模式（无 GPU 环境）

设计目的：在无 GPU / 无本地大模型的环境中，保证 RAG 管线可联调、CI/CD 可执行、评估有基线。
实现方式：stub_llm.py 不调用任何 LLM，直接将检索到的条款原文按固定结构拼接为答案，保证 100% 可溯源。幻觉防护的校验路径（条款存在性、声明判定、置信度、阻断）真实执行。
证据门控：RERANK_MIN_EVIDENCE=0.45，当 top_rerank < 0.45 时标记 needs_human_review。
假流式：按 40 字符分块 yield，前端体验同真实流式。

4.5 Agent 设计约束：不写库原则

核心设计约束：所有 Agent 的 run() 方法只输出建议/草稿/分析报告，严禁直接写数据库。写操作全部由服务层 API + 人工完成。

  • 合规要求：制药行业关键操作（偏差分级、变更审批、SAE 上报）需要人工复核与电子签名

  • 安全隔离：AI 只做辅助建议，不直接改变业务状态，避免误操作
  • 测试友好：Agent 不依赖写操作，可在无数据库环境下用 context 传入数据做单元测试

5.1 RAG 检索链路知识点

知识点 1：向量数据库 — Milvus

基本概念

Milvus 是开源的向量数据库，专门用于存储、索引和检索高维向量数据。给定一个查询向量，快速找到与之最相似的 N 个向量。

在本项目中的应用

# Milvus 集合 Schema
schema.add_field("id", DataType.INT64, is_primary=True)        # 主键
schema.add_field("vector", DataType.FLOAT_VECTOR, dim=1024)     # 1024维向量
schema.add_field("entity_id", DataType.INT64)                   # 关联MySQL条款ID
schema.add_field("text", DataType.VARCHAR, max_length=4096)     # 原文
schema.add_field("doc_version", DataType.VARCHAR, max_length=64) # 版本标识
schema.add_field("tenant_id", DataType.INT64)                  # 多租户隔离

# 索引：AUTOINDEX + COSINE 度量
idx_params.add_index(field_name="vector", index_type="AUTOINDEX", metric_type="COSINE")

关键设计点

  • AUTOINDEX：Milvus 自动选择最优索引类型（HNSW/IVF 等），无需手动调参
  • COSINE 余弦相似度：适合语义相似度计算，对向量长度不敏感
  • 多租户过滤：filter=f"tenant_id == {tenant_id}"，检索时按租户隔离
  • 异步加载：ensure_loaded() 轮询 0.5s 间隔等待加载完成，超时 30s
  • etcd + MinIO：元数据存 etcd，向量数据存 MinIO（S3 兼容）

面试要点

Q: 为什么选 Milvus 而不是 FAISS/Chroma/Pinecone？

A: ① Milvus 支持十亿级向量，可水平扩展；② 原生支持多租户过滤（filter 表达式）；③ AUTOINDEX 自动优化；④ Docker 部署简单；⑤ 开源可本地部署，满足制药行业数据不出内网要求。

知识点 2：Embedding 模型 — BGE-M3

基本概念

BGE-M3 是智源研究院（BAAI）开源的多语言、多粒度 Embedding 模型。"M3" = Multi-Linguality + Multi-Granularity + Multi-Functionality。

  • 维度：1024 维
  • 语言：支持 100+ 语言，中英文表现优异
  • 功能：稠密检索（Dense）、稀疏检索（Sparse）、多向量检索（ColBERT）三合一

在本项目中的应用

知识点 3：文档分块策略 — 基于条款的语义分块

在本项目中的实现

本项目采用基于法规结构的语义分块，而非固定长度分块：

# Step 1: Parser 解析法规结构（章/条）
CLAUSE_PATTERN = re.compile(r"第([一二三四五六七八九十百零]+|\d+)条")
SECTION_PATTERN = re.compile(r"第([一二三四五六七八九十百零]+|\d+)章")
# → 提取出"第三十五条"等条款，中文数字转整数

# Step 2: Chunker 按条款内句子边界分块
MAX_CHUNK_TOKENS = 512
APPROX_CHARS_PER_TOKEN = 1.5  # 中文约 1.5 字符/token
max_chars = int(512 * 1.5)     # = 768 字符

# 按中文标点切句，保证句子完整性
sentences = re.split(r"(?<=[。；！？\n])", content)

设计理由

  • 法规天然有结构：中国法规以"第X章→第X条"组织，按条款分块天然语义完整
  • 引用溯源需要：每个 chunk 绑定 clause_id，答案可溯源到具体条款号
  • 512 token 上限：控制 Embedding 输入长度，保证向量质量
  • 句子边界切分：不会把一句话切两半，保证语义完整

知识点 5：CrossEncoder 重排序

两阶段检索架构

用户问题 │ ▼ ┌──────────────────────────────────┐ │ 第一阶段：向量检索（双塔模型） │ ← bge-m3 Embedding + Milvus │ 快速召回 top_k=40 候选 │ 速度快，精度较低 └──────────────┬───────────────────┘ │ 预剪枝 top 8×3=24 ▼ ┌──────────────────────────────────┐ │ 第二阶段：CrossEncoder 精排 │ ← bge-reranker-large │ 对全部候选逐对打分，取 top 8 │ 速度慢，精度高 └──────────────┬───────────────────┘ │ ▼ 送入 LLM 生成

关键设计

# top_n 覆盖全部候选（非 top_n=8）
rerank_results = await reranker.rerank(query, doc_texts, top_n=len(doc_texts))
# → 所有候选都有 rerank_score，避免未重排候选绕过门控
# 失败回退：rerank 调用异常时回退到向量余弦分排序
为什么 top_n=len(doc_texts)？ 如果只取 top_n=8，其余候选没有 rerank 分，排序时回退到向量余弦分，低质量候选可能混入 top 8，绕过证据门控。全量 rerank 只增加返回序号开销，打分计算量不变。

        verdict = await llm_client.chat([
            {"role": "system", "content": "你是合规校验助手。判断声明是否被上下文支持，只回答 yes 或 no。"},
            {"role": "user", "content": f"声明：{sentence}\n\n上下文：{context_text}\n\n该声明是否有上下文依据？"},
        ], temperature=0.0)  # ← 保证确定性

置信度公式

score = 0.5 × min(rerank_score, 1.0)      # 检索相关度（最强信号）
      + 0.3 × clause_hit_rate                # 条款引用准确率
      + 0.2 × claim_pass_rate               # 声明通过率

权重设计理由：rerank_score 最强（0.5），直接反映检索内容匹配度；clause_hit_rate 次之（0.3），编造条款号是最危险幻觉；claim_pass_rate 最低（0.2），LLM 裁判本身有误差。

Stub 模式：verify_claims_stub() 用逐字匹配替代 LLM 裁判，关键词集多含"建议"。

知识点 7：置信度门控与阻断策略
条件阈值结果
置信度 < 0.6confidence < 0.6阻断 → needs_human_review
未验证声明占比 > 30%unverified_ratio > 0.3阻断 → needs_human_review
Stub 模式证据不足top_rerank < 0.45阻断 → needs_human_review
设计理念：在制药合规场景中，"不知道"比"给错答案"更安全。置信度不足时宁可标记为需人工审核，也不展示可能误导的答案。

知识点 9：SSE 流式输出

后端通过 sse-starlette 推送事件流，前端通过 EventSource 接收。相比 WebSocket，SSE 是单向推送（服务器→客户端），更适合 LLM 流式输出。

yield {"type": "citation", "citations": citations}  # 先推送引用
async for delta in llm_client.chat_stream(messages):
    yield {"type": "delta", "content": delta}        # 逐 token
yield {"type": "done", "confidence": confidence}    # 最终置信度
# 或阻断
yield {"type": "flag", "flag": "needs_human_review", ...}

断线续传通过 Last-Event-Id 实现幂等重放。Stub 模式按 40 字符分块模拟流式。

class Supervisor:
    def __init__(self):
        self.agents = AGENT_REGISTRY  # 10 个 Agent 实例

    async def execute(self, query, roles, db, context, tenant_id):
        visible = await get_visible_agents(roles)  # 角色矩阵
