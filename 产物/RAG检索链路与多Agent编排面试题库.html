一、RAG 检索链路面试题库

1.1 基础概念题

Q1: 什么是 RAG？为什么需要 RAG 而不直接用大模型？ 基础

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将信息检索与大语言模型生成结合的架构。核心思想：先从外部知识库检索与问题相关的内容，再将检索结果作为上下文送入 LLM 生成答案。

不直接用大模型的原因：

  • 知识时效性：LLM 训练数据有截止日期，无法回答最新法规
  • 幻觉问题：LLM 可能编造不存在的条款号或法规内容，在制药合规场景中不可接受
  • 私有知识：企业内部法规库、FAQ、历史案例不在 LLM 训练数据中
  • 引用溯源：RAG 可以标注答案来源（具体条款号），纯 LLM 无法溯源
  • 成本控制：RAG 只送入相关上下文，不需要 fine-tune 整个模型
  • 数据安全：法规文本留在本地向量库，不进入 LLM 训练数据
Q2: RAG 的基本流程是什么？请画出你们系统的 RAG 链路图 基础

我们系统的 RAG 链路分为检索阶段、生成阶段、校验阶段三段共 11 步：

用户问题 │ ▼ 检索阶段 ① 意图分类 → ② 查询重写 → ③ 获取激活版本 → ④ 多通道向量检索 → ⑤ 去重预剪枝 → ⑥ CrossEncoder 重排序 → top 8 │ ▼ 生成阶段 ⑦ FAQ 快速路径(rerank>0.85) 或 ⑧ LLM 生成 │ ▼ 校验阶段 ⑨ 幻觉双重校验(条款存在性 + 声明蕴含) → ⑩ 置信度计算与阻断 → ⑪ 引用溯源构建

其中意图分类区分 qa/faq_match/deviation 三种场景，查询重写做历史上下文拼接和缩写扩展（GMP→药品生产质量管理规范），多通道检索覆盖 doc/faq/case 三个 Milvus 集合，重排序用 bge-reranker-large CrossEncoder 精排。

Q3: 什么是 Embedding？它在 RAG 中起什么作用？ 基础

Embedding（词嵌入/文本嵌入）是将文本转换为固定维度的浮点向量，使语义相近的文本在向量空间中距离也相近。本项目使用 bge-m3 模型，输出 1024 维向量。

在 RAG 中的作用：

  • 入库阶段：将法规条款文本 Embedding 后存入 Milvus 向量库
  • 检索阶段：将用户问题 Embedding 后，在向量库中做余弦相似度检索，召回语义最相关的条款

Embedding 质量直接决定检索召回率，是 RAG 系统的基石。

Q4: 什么是向量相似度检索？余弦相似度和欧氏距离有什么区别？ 基础

向量相似度检索：给定一个查询向量，在向量库中找到与之"最相似"的 N 个向量。相似度由度量函数定义。

余弦相似度（Cosine Similarity）：衡量向量方向的夹角，对向量长度不敏感。公式：cos(A,B) = A·B / (|A|×|B|)，范围 [-1, 1]。

欧氏距离（Euclidean Distance）：衡量向量空间中两点的直线距离，对向量长度敏感。

本项目选 COSINE 的原因：文本 Embedding 后向量的模长可能因文本长度变化，但我们关心的是语义方向的相似性而非绝对距离。余弦相似度对文本长度不敏感，更适合语义检索。Milvus 索引配置 metric_type="COSINE"。

Q5: 什么是 CrossEncoder？它和双塔模型（Bi-Encoder）有什么区别？ 进阶

双塔模型（Bi-Encoder）：query 和 document 分别独立编码为向量，再计算相似度。优点是可预计算（document 向量提前入库），检索速度快（毫秒级）。缺点是 query 和 doc 没有交互，精度有限。

CrossEncoder（交叉编码器）：将 query 和 document 拼接后一起送入 Transformer，模型能捕获两者间的深层语义交互。精度远高于双塔，但无法预计算，需逐对推理，速度慢（百毫秒级）。

维度Bi-Encoder (bge-m3)CrossEncoder (bge-reranker-large)
输入query 和 doc 独立编码query + doc 拼接编码
速度极快（预计算）慢（逐对推理）
精度中等高
用途第一阶段召回第二阶段精排

本项目采用两阶段架构：bge-m3（Bi-Encoder）快速召回 40 条 → bge-reranker-large（CrossEncoder）精排取 top 8。

Q6: 什么是幻觉（Hallucination）？在 RAG 系统中幻觉有哪些类型？ 基础

幻觉指 LLM 生成看似合理但实际不正确或无依据的内容。在 RAG 系统中常见类型：

  • 编造条款号：答案引用了不存在的"第三十五条"（最危险，可能误导合规决策）
  • 扭曲条款原文：条款存在但 LLM 篡改了原文表述（如把"应当"改成"必须"）
  • 跨上下文拼接：把不同条款的内容错误拼接
  • 过度推理：基于检索内容做了超出原文范围的推理
  • 无依据声明：答案包含检索上下文中不存在的事实主张

本项目针对前两种和最后一种设计了双重校验：条款存在性验证（查 MySQL RegClause 表）+ 声明蕴含校验（LLM 逐句判定 yes/no）。

Q7: 什么是文档分块（Chunking）？分块大小对 RAG 有什么影响？ 基础

文档分块：将长文档切分为多个小块，每块独立 Embedding 和检索。分块大小直接影响检索精度：

  • 块太大（如整条法规）：一个向量要表达太多信息，检索精度下降；且送入 LLM 的上下文冗长，增加 token 成本
  • 块太小（如单句话）：上下文不完整，可能丢失关键限定条件（如"除生物制品外"）
  • 本项目策略：512 token 上限（约 768 中文字符），按中文标点句子边界切分，保证句子完整性。同时基于法规结构——按"第X条"为粒度，每块绑定 clause_id 支持引用溯源
Q8: 什么是 Prompt 工程？你们怎么管理 Prompt？ 基础

Prompt 工程是通过设计 LLM 输入提示词来引导生成质量和行为的技术。本项目采用版本化管理：

  • Prompt 存放于 docs/prompts/*.md 文件，而非硬编码在代码中
  • prompts.py 的 load_prompt() 优先从文件读取，缺失时回退到内嵌模板并告警
  • 4 个核心模板：role_qa（答疑）、role_faq（FAQ 口径）、role_explain（条款讲解）、claim_verifier（声明校验裁判）
  • 核心约束：只依据检索上下文作答、必须标注条款号、严禁编造、证据不足回答"未检索到依据"

版本化管理的好处：不修改代码即可调优 Prompt，支持 A/B 测试，Git 可追踪变更历史。

1.2 架构设计题

Q9: 为什么选择两阶段检索架构（向量检索 + CrossEncoder）而不是只用其中一种？ 进阶

只用向量检索的问题：bge-m3（Bi-Encoder）将 query 和 doc 独立编码，无法捕获细粒度的语义交互。对于法规条款这种高度专业化的文本，可能出现"向量相似但语义不符"的误召回。比如"批次放行"和"产品放行"向量很近，但在合规语境下含义不同。

只用 CrossEncoder 的问题：CrossEncoder 需要逐对推理，无法预计算。法规库可能有数万条 chunk，逐对打分需要数分钟，无法满足实时问答需求。

两阶段架构的优势：第一阶段用向量检索从数万条 chunk 中快速召回 40 条（毫秒级），第二阶段用 CrossEncoder 对 40 条精排取 top 8（百毫秒级），兼顾速度和精度。这是工业界 RAG 的标准做法。

中间还有预剪枝：_pre_prune_candidates() 在多通道检索后、Rerank 前做一轮剪枝——每通道保留 top 8，控制 Rerank 输入规模（24 条而非 50+），避免 Rerank 超时。

Q10: 为什么做多通道检索（doc/faq/case）？三者有什么区别？ 进阶

三类知识来源的性质和用户意图不同，分开建索引可以针对性优化检索策略：

通道内容top_k特点
doc法规条款原文（GMP/GCP 正文）40权威但表述正式，信息密度高
faq标准口径（人工审核的 Q&A 对）10通俗化解释，命中后可直接返回
case历史偏差/案例记录40实战经验，偏差调查参考

意图分类调整权重：常规问答时 doc 权重 0.7；用户问"标准口径怎么办"时 faq 权重提升到 0.6；用户问"有没有类似案例"时 case 权重提升到 0.6。

FAQ 快速路径：如果 FAQ 候选 rerank_score > 0.85，直接返回标准口径，置信度固定 0.95，跳过 LLM 生成和幻觉检测——因为 FAQ 是人工审核的，不需要再验。

Q11: 你们的幻觉防护是怎么设计的？为什么用双重校验？ 高级

设计理念：制药合规场景中，"不知道"比"给错答案"更安全。我们设计了双重校验覆盖不同类型幻觉：

第一重：条款存在性验证（verify_clause_existence）

  • 正则提取答案中所有"第X条"引用
  • 逐条查 MySQL RegClause 表验证条款是否真实存在
  • 输出 clause_hit_rate（命中率），编造的条款号会被标记为 miss
  • 针对性解决：编造条款号这类幻觉

第二重：声明蕴含校验（verify_claims）

  • 按句切分答案，过滤出包含模态词（必须/应当/不得/禁止/要求/规定）的句子
  • 用 LLM（temperature=0.0）逐句判定"该声明是否有上下文依据"（yes/no）
  • 输出 claim_pass_rate（通过率），无依据的声明被标记为 unverified
  • 针对性解决：过度推理、无依据声明这类幻觉

为什么需要两重：第一重只能检测编造的条款号，但 LLM 可能用正确的条款号但扭曲原文表述，这需要第二重的语义校验来捕获。两重校验互补，覆盖不同幻觉类型。

置信度公式：0.5×rerank_score + 0.3×clause_hit_rate + 0.2×claim_pass_rate，三维度加权。阻断规则：置信度 < 0.6 或未验证声明占比 > 30%。

Q12: 为什么置信度公式中 rerank_score 权重最高（0.5）？ 进阶

三个维度分别反映不同信号，权重设计考虑了信号强度和可靠性：

  • rerank_score (0.5)：CrossEncoder 的相关性分数，直接反映"检索到的内容与问题的语义匹配度"。这是最强信号——如果检索内容与问题不相关，即使 LLM 生成完美也只是答非所问。CrossEncoder 精度高、确定性强。
  • clause_hit_rate (0.3)：条款引用命中率，反映"LLM 是否编造了不存在的条款"。权重次高因为编造条款号是最危险的幻觉类型，但只覆盖了一种幻觉类型所以权重低于 rerank。
  • claim_pass_rate (0.2)：声明通过率，反映"LLM 的推理是否有依据"。权重最低因为 LLM 裁判本身有误差——用 LLM 判定 LLM 的输出，存在自评偏差风险，不宜给过高权重。
Q13: 为什么 Rerank 时 top_n 设为全部候选数而不是直接取 8？ 进阶

代码中 reranker.rerank(query, doc_texts, top_n=len(doc_texts))，看似浪费但实际上是安全性设计：

如果只设 top_n=8，Reranker 只返回前 8 条的 relevance_score，其余候选没有 rerank 分。排序时这些候选回退到向量余弦分——而余弦分和 rerank 分不在同一尺度（余弦分通常 0.7-0.9，rerank 分通常 0-1），可能出现"未重排候选的余弦分 > 已重排候选的 rerank 分"的情况，导致低质量候选混入 top 8，绕过证据门控。

设 top_n=len(doc_texts) 让所有候选都有 rerank_score，统一尺度排序。CrossEncoder 打分计算量不变（逐对计算），只是多返回几个序号，不影响性能。

这是一个容易踩的坑——很多 RAG 教程直接 top_n=最终需要的数量，导致排序尺度不一致。
Q14: 查询重写为什么只生成 2 个变体？不做更多？ 进阶

查询重写生成两种变体：① 历史上下文拼接（上一轮问题 + 当前问题）；② 缩写扩展（GMP→药品生产质量管理规范）。

只生成 2 个的原因：

  • 检索次数 = 变体数 × 版本数 × 通道数：假设 2 个变体 × 1 个版本 × 3 通道 = 6 次 Milvus 检索。如果变体增加到 5 个，就是 15 次检索，延迟显著增加
  • 收益递减：前 2 个变体（历史上下文 + 缩写扩展）覆盖了最常见的语义缺口，更多变体的边际收益递减
  • Rerank 兜底：即使多召回了一些低质量候选，CrossEncoder 会精排过滤掉。所以"多召回"不如"精准召回"

如果需要进一步优化：可以用 LLM 做查询改写（Query Reformulation），让 LLM 根据上下文生成更自然的完整问题，但这会增加一次 LLM 调用延迟。

Q15: 多版本知识库是怎么管理的？为什么需要多版本并行？ 进阶

法规会修订更新（如 GMP 2010 → 修订版），企业在新旧版本过渡期需要同时查询两个版本。系统通过 KbVersion 模型管理：

  • 每个版本绑定独立的 doc/faq/case 三个 Milvus 集合（如 doc_gmp_2010、doc_gmp_2024）
  • status="active" 的版本都会被检索，支持多版本并行激活
  • 检索时对每个激活版本的每个通道分别检索，去重合并后统一 Rerank
  • 版本可激活/冻结/回滚，满足法规版本管理需求

设计考量：不在同一个集合中用字段区分版本，而是物理隔离——避免版本间向量干扰，且可以独立删除旧版本集合释放存储。

Q16: Stub 模式是什么？为什么要设计这个模式？ 进阶

Stub 模式是 LLM_PROVIDER=stub 时的降级运行模式：stub_llm.py 不调用任何 LLM，直接将检索到的条款原文按固定结构拼接为答案，保证 100% 可溯源。

设计目的：

  • 无 GPU 环境联调：CI/CD 流水线没有 GPU，Stub 模式让 RAG 管线可联调、测试可执行
  • 评估基线：Stub 答案 = 检索原文，评估 Stub 答案质量 = 评估纯检索质量，排除 LLM 生成干扰
  • 幻觉防护路径验证：Stub 模式下幻觉校验（条款存在性、声明判定、置信度、阻断）仍然真实执行

证据门控：Stub 模式有额外安全门——当 top_rerank < 0.45 时标记 needs_human_review，避免无关原文被当作答案（因为没有 LLM 理解和过滤，必须更保守）。

1.3 技术实现细节题

Q17: 意图分类是怎么实现的？为什么用关键词匹配而不是 LLM 分类？ 进阶

实现方式：关键词匹配——检查用户查询中是否包含预设关键词：

FAQ_KEYWORDS = ["口径", "怎么办", "如何处理", "怎么理解", "标准", "要求是"]
CASE_KEYWORDS = ["案例", "历史", "发生过", "之前"]

命中 FAQ_KEYWORDS → faq_match 场景（faq 权重 0.6）；命中 CASE_KEYWORDS → deviation 场景（case 权重 0.6）；都不命中 → qa 场景（doc 权重 0.7）。

为什么不用 LLM 分类：

  • 延迟：LLM 分类增加一次 LLM 调用（1-3 秒），关键词匹配是微秒级
  • 确定性：关键词匹配结果确定，LLM 分类有随机性
  • 成本：每次问答都调 LLM 分类增加 API 成本
  • 够用：当前 3 种场景的关键词覆盖足够，复杂场景由 Rerank 兜底

优化方向：如果场景变复杂（如需要区分 GMP/GCP/SAE 等 10+ 种意图），可以考虑轻量分类模型（如 FastText）或 fine-tuned BERT。

Q18: 缩写扩展映射表是怎么设计的？如果遗漏了怎么办？ 进阶

当前映射表覆盖制药行业最常见的三个缩写：

abbrev_map = {
    "GMP": "药品生产质量管理规范",
    "GCP": "药物临床试验质量管理规范",
    "ICH": "人用药品注册技术国际协调会议",
}

遗漏的处理：如果用户查询中包含未映射的缩写（如 API、OOS、CAPA），系统仍会正常检索——向量检索本身能捕获缩写的语义（因为 Embedding 模型见过这些缩写），只是可能召回率略低。

优化方向：① 扩充映射表覆盖更多制药缩写；② 用 LLM 做动态缩写展开；③ 在法规文本入库时同步建立缩写-全称索引表。

Q19: 分块器是怎么保证句子完整性的？ 进阶

chunker.py 按中文标点句子边界切分，而非按固定字符数切：

MAX_CHUNK_TOKENS = 512
APPROX_CHARS_PER_TOKEN = 1.5  # 中文约 1.5 字符/token
max_chars = int(512 * 1.5)     # = 768 字符

# 按中文标点切句
sentences = re.split(r"(?<=[。；！？\n])", content)

# 逐句累加，超过 max_chars 则开新块
for sentence in sentences:
    if len(current_chunk) + len(sentence) > max_chars and current_chunk:
        chunks.append({...})  # 当前块满了，保存
        current_chunk = sentence  # 新块
    else:
        current_chunk += sentence  # 继续累加

设计要点：① 不会把一句话切两半——只在句子边界（。；！？\n）处切分；② 1.5 字符/token 是中文近似值（英文约 4 字符/token）；③ 如果单个句子超过 768 字符，不会被进一步切分（保留完整语义），只是该块稍大。

Q20: Milvus 的集合 Schema 是怎么设计的？为什么有 tenant_id 字段？ 进阶
schema.add_field("id", DataType.INT64, is_primary=True)        # 自增主键
schema.add_field("vector", DataType.FLOAT_VECTOR, dim=1024)     # bge-m3 向量
schema.add_field("entity_id", DataType.INT64)                   # 关联 MySQL 条款 ID
schema.add_field("text", DataType.VARCHAR, max_length=4096)     # 原文（检索后返回）
schema.add_field("doc_version", DataType.VARCHAR, max_length=64) # 版本标识

  • text 字段：直接在 Milvus 中存储原文（max 4096），避免二次查库，Rerank 时直接取用
  • tenant_id：支持多租户隔离，检索时 filter=f"tenant_id == {tenant_id}"。也可以用多集合隔离（每租户独立集合），但集合数过多影响性能

Q21: ensure_collection / ensure_index / ensure_loaded 三个方法的作用是什么？ 进阶

Milvus 的检索前置条件链——集合必须存在 → 必须有索引 → 必须加载到内存才能搜索：

  • ensure_collection：检查集合是否存在，不存在则创建 Schema 并建索引。幂等设计，重复调用无副作用
  • ensure_index：检查向量字段是否有索引。AUTOINDEX + COSINE 度量。索引是搜索的前提——无索引的集合无法 search
  • ensure_loaded：集合数据必须 load 到内存才能 search。load 是异步操作，ensure_loaded 轮询 get_load_state，每 0.5s 检查一次，超时 30s

调用顺序：ensure_collection → ensure_index → ensure_loaded → search。每次 search 前都会执行这三步保证可用性。

Q22: 声明校验时为什么要过滤模态词？哪些句子会跳过校验？ 高级

声明校验（verify_claims）只对包含事实主张的句子做 LLM 裁判，过滤逻辑：

# 包含条款引用 或 包含模态词的句子才校验
if CLAUSE_PATTERN.search(sentence) or any(
    kw in sentence for kw in ["必须", "应当", "不得", "禁止", "要求", "规定"]
):
    # 需要 LLM 裁判
else:
    verified += 1  # 直接通过，不校验

设计理由：

  • 减少 LLM 调用：一个答案可能有 10+ 句，逐句调 LLM 太慢。过滤后通常只有 3-5 句需要校验
  • 聚焦风险句子：包含"必须/应当/不得/禁止"等模态词的句子是合规主张——这些是错误的代价最高的句子。纯描述性句子（如"该条款规定了以下内容"）不会误导合规决策
  • 包含条款号引用的句子必须校验：因为可能是编造的条款

Stub 模式不同：verify_claims_stub() 的过滤词多了"建议"，且校验方式是逐字匹配（句子在上下文中能找到即通过），不调 LLM。

Q25: LLM 客户端的重试策略是怎么设计的？ 进阶

使用 tenacity 库实现指数退避重试：

# 同步请求：重试 3 次，退避 2-10s
@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=2, max=10))
async def chat(self, messages, temperature=0.3): ...

# 流式请求：重试 2 次，退避 1-5s
@retry(stop=stop_after_attempt(2), wait=wait_exponential(multiplier=1, min=1, max=5))
async def chat_stream(self, messages, temperature=0.3): ...

设计差异：同步请求重试 3 次（答案生成是核心路径，多给机会），流式请求重试 2 次（流式断开后重试更复杂，减少重试避免延迟叠加）。

超时设置：同步 60s，流式 120s（流式需要保持连接更久）。

声明校验的温度：temperature=0.0——声明校验需要确定性（同一输入始终输出相同结果），避免随机性影响校验稳定性。

1.4 性能优化题

Q26: RAG 链路的性能瓶颈在哪里？怎么优化？ 高级

各阶段延迟分析（典型值）：

阶段延迟瓶颈原因
Embedding50-100msHTTP 调用本地模型服务
Milvus 检索10-50ms6 次检索（2 变体×3 通道）
Rerank100-300msCrossEncoder 逐对计算
LLM 生成1-5s最大瓶颈
幻觉校验500ms-2s逐句 LLM 裁判
总计2-8s—

优化方案：

  • Embedding 缓存：高频查询的 Embedding 向量缓存到 Redis，跳过模型服务调用
  • 并行检索：6 次 Milvus 检索可 asyncio.gather 并行执行，串行→并行可节省 50ms+
  • Rerank 降量：预剪枝更激进（每通道 top 5 而非 8），减少 CrossEncoder 计算量
  • LLM 流式：首 token 延迟~200ms，用户感知"开始回答"快，总时间不变但体验好
  • 声明校验并行：逐句 LLM 裁判可并行（asyncio.gather），3-5 句并行可省 60% 时间
  • FAQ 快速路径：高置信 FAQ 命中跳过 LLM 生成和校验，延迟降到 ~300ms
Q27: 如果法规库有 10 万条条款，检索性能怎么保证？ 高级

10 万条 chunk 对 Milvus 不是问题（设计支持十亿级），但需要注意：

  • 索引选择：AUTOINDEX 自动选择 HNSW（小规模，<100 万）或 IVF（大规模）。HNSW 查询更快但内存占用大
  • 集合分片：如果单集合超过 100 万向量，考虑按法规域分集合（GMP 一个、GCP 一个），减少单集合规模
  • nprobe 参数：IVF 索引的 nprobe 控制搜索范围。nprobe 越大越精确但越慢。需要在精度和速度间平衡
  • 内存：集合必须 load 到内存才能 search。10 万条 × 1024 维 × 4 字节 ≈ 400MB，完全可行
  • Rerank 优化：预剪枝只送 24 条给 CrossEncoder，不是 10 万条。CrossEncoder 是瓶颈不是 Milvus
Q28: 多通道检索时 6 次 Milvus 查询是串行的还是并行的？怎么优化？ 高级

当前实现是串行的——retrieve() 中用 for q in queries: for version in versions: ... 嵌套循环，逐次 await search_doc/search_faq/search_case。

这是当前最大的性能优化点：

# 当前串行
for q in queries:           # 2 次循环
    for version in versions:  # 1 次循环
        await search_doc(...)   # 串行等待
        await search_faq(...)
        await search_case(...)

# 优化为并行
tasks = []
for q in queries:
    for version in versions:
        tasks.append(search_doc(db, q, version.doc_collection, tenant_id))
        tasks.append(search_faq(db, q, version.faq_collection))
        tasks.append(search_case(db, q, version.case_collection, tenant_id))
all_results = await asyncio.gather(*tasks)

6 次串行 50ms × 6 = 300ms → 并行后 ~50ms，节省 250ms。Milvus 客户端是线程安全的，支持并行查询。

Q29: Embedding 向量可以缓存吗？怎么设计？ 进阶

查询 Embedding 缓存：用户查询的 Embedding 可缓存到 Redis。同一个问题第二次查询直接取缓存，跳过模型服务调用（节省 50-100ms）。

# 伪代码
async def embed_with_cache(text: str) -> list[float]:
    cache_key = f"embed:{hashlib.md5(text.encode()).hexdigest()}"
    cached = await redis.get(cache_key)
    if cached:
        return json.loads(cached)
    vec = await embedder.embed_single(text)
    await redis.setex(cache_key, 3600, json.dumps(vec))  # 1h 过期
    return vec

入库 Embedding 不缓存：入库是一次性操作，不需要缓存。

注意：缓存 key 要用文本哈希而非原文（Redis key 有长度限制），过期时间不宜太长（模型升级后需要刷新）。

1.5 故障排查题

Q31: 用户反馈"回答完全不对题"，你怎么排查？ 高级

排查思路：从检索 → 生成 → 校验三个阶段逐步定位。

排查步骤：

  1. 检查检索结果：在 retrieve() 返回处打日志，查看 top 8 候选的 text 和 rerank_score。如果候选与问题无关 → 检索阶段问题
  2. 检查 Embedding：确认 Embedding 服务（:8081/embed）正常，向量维度 1024。可用 curl -X POST :8081/embed -d '{"input":"测试"}' 验证
  3. 检查 Milvus：确认集合已 load、索引存在、tenant_id 过滤正确。查看 ensure_loaded 是否超时
  4. 检查意图分类：查看 classify_intent 返回的场景和权重——是否因为关键词误判导致通道权重偏差
  5. 检查 LLM 输出：查看送入 LLM 的 prompt 和上下文，以及 LLM 返回的原文。可能是上下文拼接问题或 Prompt 约束不够
  6. 检查幻觉校验：如果 mode="needs_human_review"，查看 unverified_claims 列表——可能是过度阻断

常见根因：① 法规文本未正确入库（parser 解析失败）；② Milvus 集合未 load；③ Embedding 模型版本不一致；④ Prompt 约束太松导致 LLM 自由发挥。

Q32: Milvus 检索返回空结果，可能的原因有哪些？ 高级

排查步骤（按可能性排序）：

  1. 集合不存在：client.has_collection() 返回 False。原因：未执行入库流程，或集合名拼错。检查 KbVersion.doc_collection 值
  2. 集合未 load：ensure_loaded 超时日志 collection_load_timeout。原因：Milvus 容器内存不足，或集合刚创建还在加载。检查 docker logs milvus
  3. tenant_id 不匹配：filter tenant_id == {tenant_id} 过滤后无数据。原因：入库时 tenant_id 与查询时不一致
  4. 向量维度不匹配：Schema 中 dim=1024，但 Embedding 返回其他维度。原因：Embedding 模型变更
  5. Milvus 服务不可达：get_milvus() 连接失败。检查 MILVUS_URI 配置和 etcd/minio 容器状态
  6. 索引缺失：ensure_index 失败但被 try-except 吞了。检查日志 collection_index_failed
  7. 数据未插入：insert_vectors 执行但数据未落盘。检查 insert 返回的 primary_keys
Q33: Rerank 服务调用失败会怎样？有降级方案吗？ 进阶

当前实现有降级：

try:
    rerank_results = await reranker.rerank(query, doc_texts, top_n=len(doc_texts))
    for r in rerank_results:
        pruned[idx]["rerank_score"] = r.get("relevance_score", 0.0)
    pruned.sort(key=lambda x: x.get("rerank_score", 0.0), reverse=True)
except Exception as e:
    logger.warning("rerank_failed", error=str(e), candidates=len(pruned))
    # 降级：按向量余弦分排序
    pruned.sort(key=lambda x: x.get("score", 0), reverse=True)

降级逻辑：Rerank 失败时回退到向量余弦分排序（score 字段），不阻断流程。日志记录 rerank_failed 方便排查。

风险：降级后检索精度下降（余弦分不如 CrossEncoder 精确），但至少能返回结果。后续可通过监控告警发现 Rerank 服务异常。

优化方向：Rerank 服务本身用 tenacity 重试 2 次再降级；监控 Rerank 降级率，超过阈值告警。

Q34: LLM 生成超时或返回空内容怎么办？ 进阶

超时处理：llm_client.py 有 tenacity 重试（同步 3 次、流式 2 次指数退避）。如果 3 次都失败抛出 LLMError。

空内容处理：当前代码未显式检查空返回，如果 LLM 返回空字符串，会送入幻觉校验——split_sentences 过滤 len(s.strip()) > 5 的句子，空内容会返回 0 句，pass_rate = 1.0（空集默认通过），最终返回空答案 + 高置信度。

改进方案：

draft = await llm_client.chat(messages)
if not draft or len(draft.strip()) < 10:
    raise LLMError(message="LLM 返回空内容，可能是模型过载或 prompt 过长")

降级方案：LLM 不可用时可降级到 Stub 模式——返回检索原文拼接，虽然不智能但保证可用。

Q35: 幻觉校验误判率太高（正常答案被阻断），怎么排查和优化？ 高级

排查步骤：

  1. 查看被阻断的 unverified_claims：分析哪些句子被判为"无依据"。是条款存在性校验误判（clause_hit_rate 低）还是声明校验误判（claim_pass_rate 低）？
  2. 如果是条款存在性校验误判：检查 CLAUSE_PATTERN 正则是否误匹配。如"第三十五条"中的"第三十五"是否被正确提取。查 RegClause.clause_no 字段存储格式是否与正则提取结果匹配
  3. 如果是声明校验误判：查看 LLM 裁判的输入——context_text 是否只取了前 5 条候选（context[:5]），可能有用信息在第 6-8 条。调整 context[:8]
  4. 检查 temperature：声明校验必须 temperature=0.0，如果配置错误会导致随机性增加

优化方案：

  • 调整阻断阈值：如果误判集中在 claim_pass_rate，可以调整 should_block 的 unverified_ratio 阈值从 0.3 放宽到 0.4
  • 增加 context 截取数量：context[:5] → context[:8]，给 LLM 裁判更多上下文
  • 优化 claim_verifier prompt：让 LLM 裁判更宽松——"声明是否有上下文依据，宽松判定"
  • 并行校验：逐句校验太慢时改为 asyncio.gather 并行

256 token（小）检索精准，上下文聚焦语义不完整，可能丢失限定条件
512 token（本项目）平衡精度和完整性—
1024 token（大）语义完整一个向量表达太多信息，检索精度下降

选择理由：① 512 token 是 Sentence-BERT 系列模型推荐的最大输入长度，超过会截断丢失信息；② 中文法规单条通常 200-500 字（约 130-330 token），512 足够覆盖一条完整法规；③ Rerank 后只取 top 8，每条 ~512 token 送 LLM，总上下文 ~4000 token 在 LLM 上下文窗口内。

Q40: 为什么用 SSE 而不是 WebSocket 做流式输出？ 进阶
维度SSE（本项目）WebSocket
方向单向（服务器→客户端）双向
协议HTTP，穿透防火墙需升级协议，可能被防火墙拦截
断线重连浏览器原生支持需手动实现
断点续传Last-Event-Id 原生支持需自定义协议
复杂度低（标准 HTTP）高（连接管理、心跳）

选择理由：LLM 流式输出是纯单向推送（服务器→客户端），不需要客户端往服务器发消息。SSE 更简单、更兼容、原生支持断线重连和断点续传。项目中也用了 WebSocket，但那是实时通知场景（如审批通知），不是 LLM 流式。

二、多 Agent 编排面试题库

2.1 基础概念题

Q41: 什么是 Agent？它和普通函数调用有什么区别？ 基础

Agent是能够感知环境、做出决策、执行行动的自主实体。在 LLM 语境下，Agent = LLM + 工具 + 记忆 + 规划。

与普通函数调用的区别：

  • 自主性：函数被调用即执行固定逻辑；Agent 可以根据输入决定调用哪些工具、以什么顺序
  • 多步推理：函数是单步执行；Agent 可以多步推理（观察→思考→行动→观察）
  • 工具使用：Agent 可以动态选择和组合工具
  • 上下文感知：Agent 可以利用历史对话和上下文做决策

本项目的特殊设计：我们的 Agent 不是完全自主的——Supervisor 做路由决策，Agent 内部用确定性规则而非 LLM 推理。这是受控 Agent设计，在合规场景中更安全。

Q42: 什么是多 Agent 编排？常见模式有哪些？ 基础

多 Agent 编排是协调多个 Agent 协作完成复杂任务的架构。常见模式：

  • Supervisor 路由（本项目）：一个主管 Agent 接收请求，路由到专家 Agent 执行。中心化、简单可控
  • 图状态机（LangGraph）：Agent 作为图节点，条件边控制流转。显式状态管理
  • 对话式协作（AutoGen）：Agent 间通过对话协商。灵活但不可控
  • 角色扮演（CrewAI）：定义角色和任务，Agent 自主分工
  • 层级编排：多层 Supervisor 嵌套，上层做规划，下层做执行
  • 竞争式：多 Agent 各自给答案，投票或择优

本项目选 Supervisor 路由模式——因为制药场景需要强可控性，Agent 不能自主决策超出职责范围。

Q43: Supervisor 模式的优缺点是什么？ 进阶

优点：

  • 简单可控：中心化路由，所有请求经过 Supervisor，便于审计和权限控制
  • 职责清晰：每个 Agent 只管自己的领域，不关心路由逻辑
  • 易于扩展：新增 Agent 只需注册到 AGENT_REGISTRY，并在 ROLE_AGENT_MATRIX 中配置权限
  • 安全隔离：Agent 不直接通信，避免一个 Agent 影响另一个
  • 可测试：每个 Agent 独立测试，Supervisor 路由逻辑单独测试

缺点：

  • 单点瓶颈：Supervisor 是所有请求的入口，如果路由逻辑慢会成为瓶颈
  • 不支持协作：Agent 间不能直接通信，复杂任务需要多 Agent 协作时受限
  • 路由精度依赖：如果路由错误（如该走 DeviationAgent 却走了 QAAgent），用户体验差
  • 无状态记忆：Supervisor 不保留跨请求状态，多轮对话靠 context 传递
Q44: 什么是角色矩阵（ROLE_AGENT_MATRIX）？为什么需要它？ 基础

角色矩阵是一个角色到可见 Agent 列表的映射表，实现基于角色的 Agent 访问控制：

ROLE_AGENT_MATRIX = {
    "operator": ["qa", "explain"],           # 操作员只能查询
    "qa": ["qa", "deviation", "change", ...], # QA 可管理偏差/变更
    "admin": ["*"],                          # 管理员全部可见
}

为什么需要：

  • 合规要求：制药行业有严格的角色分工，操作员不应该看到偏差调查计划，PV 不应该管理变更控制
  • 安全控制：限制 Agent 可见性，即使路由错误也不会暴露越权 Agent
  • 用户体验：不同角色看到的 Agent 集合不同，界面更聚焦

权限校验：Supervisor 路由后检查 agent_key not in visible and "*" not in visible，不满足抛 ForbiddenError。

Q45: 为什么 Agent 不能写数据库？这个设计约束的背景是什么？ 进阶

核心原则：所有 Agent 的 run() 方法只输出建议/草稿/分析报告，严禁直接操作数据库。写操作由服务层 API + 人工完成。

设计背景：

  • FDA 21 CFR Part 11：制药行业电子记录要求人工复核和电子签名，AI 不能自主做关键决策
  • 可审计性：所有状态变更必须经 API 层，留下哈希链审计日志。Agent 直接写库无法留下合规审计痕迹
  • 安全隔离：AI 只做辅助建议，不直接改变业务状态。即使 AI 出错（幻觉、误判），不会污染数据库
  • 四眼原则：关键操作（偏差分级、变更审批、SAE 上报）需要第二人复核 + 电子签名
  • 测试友好：Agent 不依赖写操作，可以在无数据库环境下用 context 传入数据做单元测试

代码体现：每个 Agent 的返回中都有 "writes_disabled": True 和 "persist_hint"，明确告知调用方"这是建议，请走 API 落库"。

2.2 架构设计题

Q46: 当前路由策略是"QA 优先"，会不会有问题？怎么改进？ 高级

当前策略：route_query() 中如果 "qa" in visible_agents 就直接路由到 QAAgent，不考虑用户意图。

问题：QA 角色的用户可见 [qa, deviation, change, path, compliance_analysis] 五个 Agent，但无论问什么都会路由到 QAAgent。如果用户问"帮我做偏差分级"，应该走 DeviationAgent，但实际走了 QAAgent（RAG 问答管线），可能只是检索到偏差相关条款而非做分级。

改进方案：

  1. 基于意图的路由：用 LLM 或轻量分类器分析 query 意图，映射到对应 Agent。已有 SCENARIO_TO_AGENT 映射表但未启用
  2. 关键词路由：类似 RAG 的意图分类——"偏差/偏离/异常"→DeviationAgent，"变更/修改/变更控制"→ChangeAgent
  3. 两阶段路由：先用 QAAgent 做 RAG 检索，如果检索到偏差/变更相关内容，二次路由到对应 Agent
  4. 多 Agent 并行：同时调 QAAgent + DeviationAgent，合并结果返回

当前为什么没改进：QAAgent 的 RAG 管线能力最强（能检索+生成+校验），对于大多数场景已经够用。偏差/变更等 Agent 的功能通过对应 API 接口直接调用，不依赖 Supervisor 路由。

Q47: BaseAgent 的 tools 字段是描述性字符串而不是函数对象，这样设计有什么考虑？ 进阶

当前设计：

class DeviationAgent(BaseAgent):
    tools = ["classify_severity", "search_case", "draft_investigation_plan"]  # 字符串
    # 实际工具函数在 Agent 内部定义
    async def run(self, query, context, db, tenant_id):
        severity_advice = classify_severity(description)  # 直接调用内部函数
        ...

设计考虑：

  • 简单：不需要额外的 Tool 注册/发现机制，Agent 内部直接调用函数
  • 确定性强：工具调用顺序固定（分级→检索→计划），不是 LLM 动态决策
  • 可测试：每个工具是普通 Python 函数，直接 import 测试
  • 文档作用：tools 字段更多是文档性质——告诉使用者这个 Agent 做什么

对比 LangChain Tool：LangChain 的 Tool 对象支持 LLM 动态选择工具（ReAct 模式），但本项目用确定性规则调用工具，不需要 LLM 决策——更安全、更快、更可预测。

如果需要动态工具选择：可以升级为 LangChain Tool 对象 + LLM ReAct，但需要权衡确定性和灵活性。

Q48: 服务层状态机和 Agent 层是什么关系？为什么不把状态机放到 Agent 里？ 高级

关系：Agent 做建议，服务层做执行。以偏差管理为例：

  • DeviationAgent：分析偏差描述 → 给出分级建议（critical/major/minor）→ 检索同类案例 → 生成调查计划草案。不写库
  • quality_service.py：classify_deviation() 正式写入分级 → investigate_deviation() 落库调查计划 → close_deviation() 关闭偏差。写库 + 状态机

为什么不放 Agent 里：

  • 合规要求：状态变更需要人工复核 + 电子签名，不能由 Agent 自动执行
  • 事务一致性：状态机涉及数据库事务（如偏差从 investigating → qa_review 需要同时写审计日志），Agent 层不管理事务
  • 可审计：服务层操作写入哈希链审计日志，Agent 建议不写日志
  • 关注点分离：Agent 关注"分析建议"，服务层关注"状态管理和持久化"

协作流程：API 收到请求 → 调 Agent 生成建议 → 返回前端 → 人工审核确认 → 调服务层 API 落库 → 服务层走状态机 + 审计日志。

Q49: 如果要新增一个 Agent（如"供应商审计 Agent"），需要改哪些地方？ 进阶

需要改动 4 个地方：

  1. 新建 Agent 文件：backend/app/agents/supplier_audit_agent.py，继承 BaseAgent，实现 run() 方法
  2. 注册到 AGENT_REGISTRY：supervisor.py 中 "supplier_audit": SupplierAuditAgent()
  3. 配置角色权限：ROLE_AGENT_MATRIX 中给相关角色（如 compliance、admin）添加 "supplier_audit"
  4. API 路由：在 api/v1/ 下新建对应路由文件，调用 Supervisor 或直接调用 Agent
# Step 1: 新建 Agent
class SupplierAuditAgent(BaseAgent):
    name = "供应商审计"
    description = "供应商审计检查表草稿与缺口识别"
    tools = ["build_checklist", "identify_gaps"]
    async def run(self, query, context=None, db=None, tenant_id=1):
        ...

# Step 2: 注册
AGENT_REGISTRY["supplier_audit"] = SupplierAuditAgent()

# Step 3: 角色矩阵
ROLE_AGENT_MATRIX["compliance"].append("supplier_audit")

不需要改动：BaseAgent、Supervisor 核心逻辑、其他 Agent。这就是 Supervisor 模式的扩展性优势。

Q50: context 字典传参设计有什么优缺点？有没有更好的方案？ 进阶

当前设计：run(query, context, db, tenant_id)，context 是 dict[str, Any]，灵活携带任意数据。

优点：

  • 灵活：不同 Agent 需要不同上下文，dict 不限定字段
  • 可选传参：context 为 None 时 Agent 用默认值，不强制传
  • 兼容性好：新增字段不需要改接口签名

缺点：

  • 无类型检查：dict 字段拼写错误不会报错（如 context.get("devation") 拼错），mypy 无法检查
  • 文档依赖：每个 Agent 的 context 需要什么字段只有看代码才知道
  • 测试复杂：需要构造正确的 context dict，字段不对 Agent 静默用默认值

优化方案：用 Pydantic BaseModel 或 dataclass 替代 dict：

@dataclass
class DeviationContext:
    description: str
    title: str | None = None
    category: str | None = None
    similar_cases: list[dict] | None = None

但有成本——不同 Agent 需要不同 context 类型，接口签名变复杂。当前灵活性和安全性的权衡是合理的。

2.3 技术实现细节题

Q51: DeviationAgent 的分级逻辑是怎么实现的？ 进阶

classify_severity() 基于关键词匹配做分级初判：

CRITICAL_KEYWORDS = (
    "产品放行", "批次放行", "已上市", "市场", "召回", "患者",
    "无菌", "污染", "数据完整性", "重大", "造假", "交叉污染",
    "微生物", "假药", "劣药",
)
MAJOR_KEYWORDS = (
    "关键工艺", "工艺参数", "超限", "oos", "ooe", "未按sop",
    "违反", "验证失败", "关键设备", "中间体", "混批", "混料",
)

逻辑：命中 critical 关键词 → critical 级别；否则命中 major 关键词 → major 级别；都不命中 → minor 级别。

置信度：min(0.95, 0.6 + 0.1×len(critical_hits) + 0.05×len(major_hits))，命中越多置信越高。

设计理由：① 确定性强（不调 LLM，结果可预测）；② 速度快（关键词匹配微秒级）；③ 可解释（返回命中关键词作为分级理由）；④ 不写库（返回 writes_disabled: True，由人工通过 API 确认）。

局限：纯关键词匹配无法理解语义，如"没有发生污染"命中"污染"会误判为 critical。优化方向：用 LLM 做语义分级。

Q52: ComplianceAgent 是怎么跨域聚合数据的？ 高级

ComplianceAgent 聚合 4 个业务域的数据生成合规报告：

  1. 培训认证域：调用 training_service.get_analytics() 和 get_cert_matrix()，获取证书有效数/到期数/认证率
  2. 质量域：调用 quality_service.list_deviations/list_changes/list_capas()，获取偏差分级分布/未关闭偏差/未关闭 CAPA
  3. 药物警戒域：调用 sae_service.list_sae()，获取 SAE 状态分布/紧急时限
  4. 审计域：调用 audit_service.list_audit_checks()，获取进行中检查单/未闭合缺口

设计特点：

  • 只读聚合：不写库，只调用各服务的 list/get 只读方法
  • context 传参优化：如果 context 中已携带数据（ctx.get("deviations")），就不重复查库。避免 API 层已经查过的数据 Agent 再查一次
  • 关注点与建议：自动生成 attention_items（关注点）和 recommendations（建议），如"有 3 项认证将到期 → 安排复训"
  • 频率统计：_freq() 函数统计各状态/分级的频次分布
Q53: SCENARIO_TO_AGENT 映射表为什么定义了但没用？ 进阶

SCENARIO_TO_AGENT 定义了意图到 Agent 的映射（如 "deviation": "qa"），但 Supervisor.execute() 的路由逻辑用的是 route_query()（QA 优先策略），没有使用这个表。

原因分析：

  • 预留扩展：为未来基于意图的精细路由预留。当前 QA 优先够用，后续可以改为查 SCENARIO_TO_AGENT
  • 当前场景路由通过 API 层实现：前端不同页面直接调不同 API（/quality/* 调 quality_service，/sae/* 调 sae_service），不经过 Supervisor。Supervisor 主要用于 /qa/ask 统一入口
  • RAG 意图分类已有：classify_intent() 在 RAG 管线内做了意图分类（qa/faq_match/deviation），影响通道权重。不需要 Supervisor 再做一次

改进方向：如果要启用 SCENARIO_TO_AGENT，需要先用 LLM 或分类器分析 query 意图（返回 scenario），再查表路由。这会让 Supervisor 路由更精准。

Q54: admin 角色的 "*" 权限是怎么实现的？ 基础

在 get_visible_agents() 中特殊处理：

async def get_visible_agents(roles: list[str]) -> set[str]:
    agents: set[str] = set()
    for role in roles:
        role_agents = ROLE_AGENT_MATRIX.get(role, [])
        if "*" in role_agents:
            # 通配符：返回全部 10 个 Agent
            return {"qa", "explain", "path", "deviation", "change",
                    "audit", "sae", "kb_ops", "training", "compliance_analysis"}
        agents.update(role_agents)
    return agents

在 Supervisor.execute() 的权限校验中：if agent_key not in visible and "*" not in visible，如果 visible 包含 "*" 则跳过校验。

设计要点：① "*" 是特殊标记，遇到即展开为全部 Agent；② 一个用户可能有多个角色，取并集；③ admin 角色虽然能访问全部 Agent，但 Agent 本身的不写库约束仍然生效。

2.4 故障排查题

Q55: Supervisor 路由到不存在的 Agent 会怎样？ 进阶

当前处理：

agent = self.agents.get(agent_key)
if not agent:
    return {
        "error": f"Agent {agent_key} not implemented or not registered",
        "available_agents": sorted(self.agents.keys()),
    }

返回错误信息 + 可用 Agent 列表。不会抛异常，而是返回 dict。

问题：① 返回的 dict 结构和正常 Agent 返回的 {"agent": name, "output": {...}} 不一致，前端处理困难；② 不抛异常意味着上游不知道出错了。

改进方案：

  • 抛出 AppError(message=f"Agent {agent_key} not found")，让 FastAPI 异常处理器统一处理
  • 启动时校验 ROLE_AGENT_MATRIX 中的 Agent key 都在 AGENT_REGISTRY 中，不匹配则启动失败
Q56: Agent 的 run() 方法抛出异常会怎样？有异常处理吗？ 进阶

当前实现：Supervisor.execute() 中直接 result = await agent.run(query, context, db, tenant_id)，没有 try-except 包裹。如果 Agent 内部抛出未捕获异常，会直接传播到 API 层。

影响：

  • API 层如果也没有捕获，FastAPI 会返回 500 Internal Server Error
  • 用户体验差——看到 500 错误而非有意义的错误信息
  • 数据库事务可能未正确回滚

改进方案：

try:
    result = await agent.run(query, context, db, tenant_id)
except AppError:
    raise  # 业务异常直接抛出
except Exception as e:
    logger.error("agent_execution_failed", agent=agent_key, error=str(e))
    return {
        "agent": agent_key,
        "output": {"error": "Agent 执行异常，请稍后重试",
                   "detail": str(e)}
    }
Q57: 用户反馈"权限不足"但应该有权限，怎么排查？ 进阶

排查步骤：

  1. 检查用户角色：查 SysUser.roles，确认角色是否正确分配。可能是角色配置遗漏
  2. 检查角色矩阵：查 ROLE_AGENT_MATRIX 中该角色是否包含目标 Agent。如新加的 Agent 可能忘记在矩阵中注册
  3. 检查路由结果：查看 route_query() 返回的 agent_key，是否路由到了用户不可见的 Agent
  4. 检查 "*" 通配：admin 角色应该有 "*"，如果没有可能是配置被覆盖
  5. 检查多角色合并：用户可能有多个角色，get_visible_agents() 取并集。如果一个角色有权限另一个没有，合并后应该有权限

常见根因：① 新增 Agent 后忘记在 ROLE_AGENT_MATRIX 中配置；② 用户角色分配错误（该给 qa 角色却给了 operator）；③ route_query() 的 QA 优先策略路由到了用户无权访问的 Agent。

Q58: 偏差分Agent 分级建议不准（如 critical 偏差被判为 minor），怎么排查？ 高级

排查步骤：

  1. 查看分级结果：DeviationAgent 返回的 severity_suggestion 中的 keywords 和 reasons，看命中了哪些关键词
  2. 分析偏差描述：查看输入的 description 文本，是否包含 critical 关键词。可能用户描述用语不在关键词表中（如"可能影响患者安全"而非"患者"）
  3. 检查关键词表：CRITICAL_KEYWORDS 和 MAJOR_KEYWORDS 是否需要扩充
  4. 检查 description 传入：确认 context 中 description 正确传入，不是 None 或空字符串（会走 minor 默认）

优化方案：

  • 扩充关键词表：增加更多 critical/major 特征词
  • 引入语义分级：用 LLM 做语义分级——"根据偏差描述判断严重度，critical/major/minor"
  • 混合策略：先用关键词做初判，如果置信度低（无命中）再调 LLM 做语义分级
  • 案例对比：用 search_similar_cases() 检索同类历史偏差，参考历史分级
注意：分级只是建议，最终分级由 QA 人工确认。Agent 分级不准不会直接导致错误分级——但会影响调查计划草案的质量。

2.5 对比选型题

Q59: 为什么不用 LangGraph 做 Agent 编排？ 高级

LangGraph 的特点：基于图状态机，Agent 作为节点，条件边控制流转，支持循环、分支、人在回路。适合复杂多步推理场景。

不用 LangGraph 的原因：

  • 不需要复杂流转：我们的 Agent 间不需要协作和状态共享，路由逻辑简单（角色→可见 Agent→路由），自研 Supervisor 更轻量
  • 确定性优先：制药场景需要强可控性，LangGraph 的图流转可能有循环和分支，增加不确定性
  • 状态机在服务层：业务状态机（偏差/变更/SAE）在 service 层用 Python dict 实现，不需要 LangGraph 的图状态管理
  • 依赖收敛：虽然 pyproject.toml 引了 langgraph >= 0.2，但实际未在核心代码中使用，减少框架耦合

LangGraph 更适合的场景：需要多步推理（如"查法规→分析差距→生成方案→人工审核→修改"）、Agent 间需要传递中间结果、需要条件循环（如重试直到满足条件）。

如果引入 LangGraph：可以把偏差处理流程建模为图——偏差上报→Agent分级→人工确认→Agent调查计划→人工审核→Agent CAPA建议→关闭。每个节点是一个 Agent 或人工步骤，条件边控制流转。

Q60: 为什么不用 AutoGen 或 CrewAI？ 进阶
框架模式优势不选的原因
自研 Supervisor（本项目）中心化路由简单可控、确定性—
AutoGen对话式协作灵活、Agent 间可协商不可控、LLM 调用多、成本高
CrewAI角色扮演自然、角色分工过度依赖 LLM 决策、确定性差
LangGraph图状态机显式状态、可循环复杂度高、当前不需要

核心原因：制药合规场景需要强确定性和强可控性。AutoGen 和 CrewAI 都依赖 LLM 做路由和决策，引入随机性和不可预测性。自研 Supervisor 用规则路由，结果可预测、可审计、可测试。

可借鉴的方面：AutoGen 的"多轮对话"思路可用于未来需要 Agent 间协商的场景；CrewAI 的"角色+任务"建模可用于更复杂的工作流编排。

三、系统故障问题专题

3.1 RAG 链路故障

Q62: 【故障】法规文档入库后检索不到，怎么排查？ 高级

排查思路：入库流程 = 解析→分块→Embedding→Milvus 写入，逐段检查。

排查步骤：

  1. 检查 Parser 解析：查 extract_sections_and_clauses() 是否正确提取条款。中文数字正则 第([一二三四五六七八九十百零]+|\d+)条 是否匹配。如果法规文档格式变化（如用"1."而非"第一条"），解析会失败
  2. 检查 Chunker 分块：查 chunk_clause() 是否产生非空 chunk。如果 content 为空或全部 < 5 字符，会被 split_sentences 过滤
  3. 检查 Embedding：查 embedder.embed() 是否成功返回 1024 维向量。如果模型服务 (:8081) 未启动或模型文件缺失，Embedding 会失败
  4. 检查 Milvus 写入：查 insert_vectors() 是否成功。检查 ensure_collection 是否创建了集合、ensure_loaded 是否完成加载
  5. 检查集合名：入库时用的集合名（如 doc_gmp_2010）与检索时 KbVersion.doc_collection 是否一致
  6. 检查 tenant_id：入库时 tenant_id 与检索时是否一致
  7. 直接查 Milvus：用 pymilvus 直接 client.query(collection_name, filter="", limit=10) 查看数据是否存在

常见根因：① Parser 正则不匹配新法规格式；② Embedding 服务未启动；③ 集合名不一致；④ tenant_id 不匹配。

优化规避：入库后加验证步骤——随机抽样 5 条 chunk 做检索验证，确保入库成功。

Q63: 【故障】检索结果全是同一条法规的不同 chunk，缺乏多样性，怎么解决？ 高级

问题分析：向量检索按相似度排序，同一条法规的不同 chunk 语义相近，容易扎堆出现在 top 结果中。用户问"GMP 对洁净室的要求"，检索结果可能全是第一百三十条的 3 个 chunk，而遗漏了其他相关条款。

解决方案：

  • MMR（Maximal Marginal Relevance）：在检索时不仅考虑与 query 的相似度，还考虑结果间的多样性。score = α×sim(q,d) - (1-α)×max(sim(d,selected))。Milvus 2.4 不原生支持 MMR，可在应用层实现
  • 按条款去重：同一 clause_id 的 chunk 只保留 rerank_score 最高的一个。在 _pre_prune_candidates() 中增加条款维度去重
  • 按章节分散：在预剪枝时按 section_id 分组，每章节最多保留 N 条
  • 增加 top_k：从 40 增加到 60，扩大召回池再靠 Rerank 精排
# 按条款去重实现
def _dedupe_by_clause(candidates):
    seen_clauses = set()
    deduped = []
    for c in sorted(candidates, key=lambda x: x.get("score", 0), reverse=True):
        clause_key = c.get("entity_id") or c.get("text")[:100]
        if clause_key not in seen_clauses:
            deduped.append(c)
            seen_clauses.add(clause_key)
    return deduped
Q64: 【故障】Rerank 服务超时（>5s），导致整体响应变慢，怎么解决？ 高级

问题分析：bge-reranker-large CrossEncoder 逐对计算，24 条候选 × ~50ms/对 ≈ 1.2s。如果模型加载到 GPU 失败回退到 CPU，可能 5s+。

排查步骤：

  1. 检查 GPU 利用率：nvidia-smi 查看模型服务进程是否在 GPU 上。如果不在，检查 CUDA 环境
  2. 检查候选数量：查 _pre_prune_candidates 输出条数。如果多通道多版本导致候选过多（50+），Rerank 计算量暴增
  3. 检查模型服务：curl -X POST :8081/rerank -d '{"query":"test","documents":["a","b"]}' 测试延迟
  4. 检查并发：多用户并发查询时 Rerank 请求排队，单次 Rerank 没问题但队列等待导致超时

解决方案：

  • 更激进预剪枝：每通道 top 5 而非 8，减少到 15 条候选
  • Rerank 超时+降级：给 Rerank 加 2s 超时，超时后降级到向量余弦分排序
  • 模型量化：bge-reranker-large → bge-reranker-base，模型小一半，速度快 2x
  • 批处理优化：models_server.py 中 CrossEncoder.predict 设置 batch_size 更大值利用 GPU 并行
  • 多实例：部署多个 models_server 实例，负载均衡
Q65: 【故障】LLM 生成答案包含编造的条款号（如"第三百七十八条"实际不存在），幻觉校验是否一定能拦截？ 高级

不一定能完全拦截。分析：

条款存在性校验（verify_clause_existence）能拦截的场景：

  • 答案中写了"第三百七十八条"，正则 第[一二三四五六七八九十百零\d]+条 能提取
  • 查 MySQL RegClause 表，clause_no 不匹配 → miss → clause_hit_rate 下降

可能漏检的场景：

  • 正则不匹配：如果 LLM 写"第37条"（阿拉伯数字）或"第三七八条"（不规范中文数字），正则可能不匹配 → 不校验 → 直接通过
  • 条款号格式不一致：数据库存 "第三百七十八条"，LLM 写"第378条"，clause_no.contains() 可能不匹配
  • 条款号真实但内容编造：LLM 引用了正确的条款号但编造了原文内容——条款存在性校验通过，需要声明校验捕获

优化方案：

  • 完善正则：同时匹配阿拉伯数字和中文数字：第([\d一二三四五六七八九十百零]+)条
  • 规范化条款号：校验前用 normalize_clause_no() 统一转换为整数比较
  • 原文比对：不仅校验条款存在，还比对答案中引用的原文与数据库中的原文是否一致（文本相似度）
Q66: 【故障】Embedding 服务崩溃，整个 RAG 系统不可用，怎么设计高可用？ 高级

影响范围：Embedding 服务 (:8081) 崩溃 → 无法做查询向量化 → 检索阶段失败 → 整个 RAG 不可用。

排查步骤：

  1. 检查服务状态：curl :8081/health 或 docker ps 查看容器状态
  2. 检查 GPU：nvidia-smi 查看 GPU 内存是否被其他进程占用
  3. 检查模型文件：models/bge-m3/model.safetensors 是否存在且完整
  4. 查日志：docker logs models_server 查看 OOM 或 CUDA error

高可用方案：

  • 多实例部署：部署 2+ 个 models_server 实例，Nginx 负载均衡。一个崩溃另一个接管
  • Embedding 缓存：高频查询的 Embedding 缓存到 Redis，Embedding 服务短暂不可用时可降级
  • 健康检查+自动重启：docker-compose 配置 healthcheck + restart: always
  • 降级模式：Embedding 服务不可用时，降级到 BM25 关键词检索（不需要向量）
  • 预计算：用户查询的 Embedding 在前端输入时就异步预计算
关键设计：Embedding 服务是 RAG 的单点依赖。生产环境必须多实例 + 健康检查 + 自动重启。

3.2 Agent 编排故障

Q67: 【故障】Agent 路由错误（用户要偏差分级但路由到 QAAgent），怎么排查和解决？ 高级

问题现象：QA 角色用户问"帮我分析这个偏差的严重度"，route_query() 因为"qa"在 visible 中优先路由到 QAAgent，但用户实际需要 DeviationAgent。

排查步骤：

  1. 查看路由日志：确认 route_query() 返回的 agent_key
  2. 查看 visible_agents：确认用户角色对应的可见 Agent 列表
  3. 分析路由策略：当前 route_query() 是"QA 优先"，只要有 qa 就路由到 QAAgent

根本原因：route_query() 的 QA 优先策略不考虑用户意图，任何查询都路由到 QAAgent。

解决方案：

  • 方案一：关键词路由——在 route_query() 中加关键词匹配： 
    if "偏差" in query or "偏离" in query:
    return "deviation"
if "变更" in query:
    return "change"
if "qa" in visible_agents:
    return "qa"
  • 方案二：LLM 路由——用 LLM 分析 query 意图，返回 Agent key。延迟增加 ~1s
  • 方案三：API 层分流——前端不同入口直接调不同 API，不走 Supervisor 路由
  • 方案四：启用 SCENARIO_TO_AGENT——先做意图分类，再查映射表路由

推荐方案：方案一（关键词路由）——简单、快速、确定性强，与 RAG 的意图分类风格一致。

Q68: 【故障】Agent 返回数据结构不一致（有的返回 output，有的直接返回 error），前端怎么处理？ 进阶

问题分析：

  • 正常返回：{"agent": "偏差处理", "output": {...}}
  • Agent 不存在：{"error": "Agent xxx not implemented", "available_agents": [...]}
  • Agent 内部异常：可能抛异常（无返回值）

影响：前端需要判断多种返回格式，容易遗漏边界条件。

解决方案：统一返回格式 + 异常处理

# Supervisor.execute() 统一异常处理
try:
    result = await agent.run(query, context, db, tenant_id)
    if "output" not in result:
        return {"agent": agent_key, "output": {"error": "Agent 返回格式异常"}}
    return result
except AppError as e:
    return {"agent": agent_key, "output": {"error": e.message}}
except Exception as e:
    logger.error("agent_failed", agent=agent_key, error=str(e))
    return {"agent": agent_key, "output": {"error": "Agent 执行异常", "detail": str(e)}}

前端处理：统一检查 result.output.error 是否存在，存在则展示错误信息，否则正常渲染 output。

Q69: 【故障】Agent 依赖的数据库连接断开，怎么处理？ 进阶

问题分析：多个 Agent 的 run() 方法需要 db: AsyncSession 参数。如果数据库连接池耗尽或 MySQL 不可达，db.execute() 会抛 OperationalError。

当前处理：Agent 内部没有 try-except 包裹 db 操作，异常直接传播到 API 层。

排查步骤：

  1. 检查 MySQL 容器状态：docker ps | findstr mysql
  2. 检查连接池配置：create_async_engine(pool_size=10, max_overflow=20) 是否够用
  3. 检查是否有连接泄漏：Agent 中 await db.execute() 后 session 未正确关闭

解决方案：

  • 连接池监控：监控连接池使用率，接近上限时告警
  • Agent 降级：db 不可用时，部分 Agent 可以用 context 传入的数据降级运行（如 ComplianceAgent 的 ctx.get("deviations")）
  • 重试机制：db.execute 加 tenacity 重试（网络抖动场景）
  • 健康检查：API 层加 /health 端点检查 db 连通性
Q70: 【故障】状态机非法转换（如从 closed 状态尝试变更为 investigating），怎么处理？ 进阶

当前处理：ALLOWED_TRANSITIONS 中 closed 的转换集合为空 set()。服务层在执行状态变更前会检查：

def validate_transition(current_status, target_status, transitions):
    allowed = transitions.get(current_status, set())
    if target_status not in allowed:
        raise AppError(
            message=f"非法状态转换: {current_status} → {target_status}",
            code=400
        )

排查步骤：

  1. 查看 API 返回的错误信息和状态码（400）
  2. 检查 ALLOWED_TRANSITIONS 中当前状态是否允许目标转换
  3. 检查是否有并发请求导致状态竞争（两个请求同时尝试变更同一实体状态）

并发问题解决方案：

  • 乐观锁：在 UPDATE 语句中加 WHERE status = {expected_status}，如果行数=0 说明状态已被其他请求变更
  • 悲观锁：SELECT ... FOR UPDATE 锁定行，事务完成才释放
  • 审计日志：非法转换尝试也记录审计日志，用于安全审计

3.3 基础设施故障

Q71: 【故障】Milvus 容器 OOM（内存不足）导致向量检索失败，怎么解决？ 高级

问题分析：Milvus 需要将集合数据 load 到内存才能搜索。集合多或数据量大时内存不足，容器被 OOM Killer 杀掉。

排查步骤：

  1. 检查容器状态：docker ps -a | findstr milvus，如果 STATUS 是 Exited(137) 说明被 OOM Kill
  2. 检查容器内存限制：docker inspect milvus | findstr Memory，docker-compose.yml 中是否设了 mem_limit
  3. 检查集合数量：多版本×3通道可能产生大量集合，每个集合 load 都占内存
  4. 检查数据量：10 万条 × 1024 维 × 4 字节 ≈ 400MB/集合。如果 10 个集合就是 4GB

解决方案：

  • 增加内存：docker-compose.yml 中 mem_limit: 8g 或增大宿主机内存
  • 按需 load：不活跃的版本集合 release_collection() 释放内存，只在检索时 load
  • 集合合并：同一法规不同版本合并到一个集合，用 doc_version 字段区分，减少集合数
  • Milvus 分布式：多节点部署，数据分片到多个 Milvus 实例
  • 监控：Prometheus 采集 Milvus 内存指标，接近上限告警
注意：Milvus 的 ensure_loaded() 有 30s 超时，如果 load 因内存不足反复失败，会超时但不报错（只打 warning），导致后续 search 返回空。需要监控 load_timeout 日志。
Q72: 【故障】etcd 或 MinIO 宕机导致 Milvus 不可用，怎么处理？ 高级

依赖关系：Milvus 元数据存在 etcd，向量数据存在 MinIO（S3 兼容）。任何一个宕机 Milvus 都不可用。

排查步骤：

  1. 检查 etcd：docker ps | findstr etcd + curl :2379/health
  2. 检查 MinIO：docker ps | findstr minio + curl :9000/minio/health/live
  3. 检查 Milvus 日志：docker logs milvus 2>&1 | findstr "error\|etcd\|minio"

解决方案：

  • 重启依赖：docker-compose restart etcd minio milvus（按顺序）
  • 数据恢复：如果 MinIO 数据卷损坏，从备份恢复。etcd 数据损坏需要重建 Milvus 集合（从 MySQL 重新灌入向量）
  • 数据卷持久化：docker-compose.yml 中 etcd 和 minio 配置 volumes 持久化到宿主机，避免容器删除后数据丢失
  • 高可用：生产环境部署 etcd 集群（3 节点）和 MinIO 分布式模式
  • RAG 降级：Milvus 不可用时降级到 MySQL LIKE 查询（精确关键词匹配），虽然精度差但保证可用
Q73: 【故障】Redis 连接池耗尽导致缓存功能不可用，怎么排查和解决？ 进阶

影响范围：会话缓存失效、限流失效、Embedding 缓存不可用。系统不会完全不可用，但性能下降。

排查步骤：

  1. 检查 Redis 容器：docker ps | findstr redis + redis-cli ping
  2. 检查连接数：redis-cli info clients，如果 connected_clients 接近 maxclients 说明连接泄漏
  3. 检查内存：redis-cli info memory，如果 used_memory 接近 maxmemory 会触发淘汰
  4. 检查代码：查看是否有 Redis 连接未正确释放（async with redis_client 未用 with）

解决方案：

  • 连接池配置：max_connections=50，超过会等待而非报错
  • 超时设置：Redis 操作加 socket_timeout=5，避免连接挂起
  • 降级策略：Redis 不可用时降级到内存缓存（lru_cache）或直接跳过缓存
  • 监控：Prometheus 采集 Redis 连接数、内存、命中率
Q74: 【故障】MySQL 数据库连接池耗尽（Too many connections），怎么解决？ 进阶

排查步骤：

  1. 查看 MySQL 连接数：SHOW STATUS LIKE 'Threads_connected'，与 max_connections 比较
  2. 查看活跃连接：SHOW PROCESSLIST，找长时间运行的查询（可能是慢查询导致连接不释放）
  3. 检查 SQLAlchemy 连接池：create_async_engine(pool_size=10, max_overflow=20, pool_timeout=30)。如果 pool_timeout 触发会抛 TimeoutError
  4. 检查异步 session 管理：async with get_db() as session 是否正确释放。如果有 await db.execute() 但没用 with，session 不会关闭

解决方案：

  • 增大连接池：pool_size=20, max_overflow=40（根据并发量调整）
  • 慢查询优化：加索引、避免 N+1 查询、用 EXPLAIN 分析慢 SQL
  • 连接超时：pool_recycle=3600，每小时回收连接避免 MySQL 端 wait_timeout 导致连接失效
  • 读写分离：读操作走从库，减轻主库连接压力
  • 监控告警：连接池使用率 > 80% 告警
Q75: 【故障】Docker 容器启动顺序错误导致服务依赖失败，怎么解决？ 进阶

问题现象：后端容器启动时 MySQL/Milvus 还未就绪，导致连接失败退出。

原因：docker-compose 的 depends_on 只保证容器启动顺序，不保证服务就绪。MySQL 容器启动后需要几秒初始化。

解决方案：

  • 健康检查：docker-compose.yml 中每个服务加 healthcheck
  • condition: service_healthy：depends_on: mysql: condition: service_healthy，等 MySQL 健康检查通过才启动后端
  • 重试机制：后端启动时如果连不上 MySQL，tenacity 重试 5 次（间隔 5s）
  • 启动脚本：entrypoint 脚本中 until mysqladmin ping; do sleep 2; done 等待 MySQL 就绪
# docker-compose.yml 示例
services:
  mysql:
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      timeout: 5s
      retries: 5

  backend:
    depends_on:
      mysql:
        condition: service_healthy
      milvus:
        condition: service_healthy
Q76: 【故障】本地模型服务（models_server.py）启动失败（CUDA error / 模型加载失败），怎么排查？ 高级

排查步骤：

  1. 检查 GPU：nvidia-smi 查看 GPU 状态、驱动版本、CUDA 版本
  2. 检查 PyTorch CUDA：python -c "import torch; print(torch.cuda.is_available())"。如果 False 说明 PyTorch 未正确安装 CUDA 版本
  3. 检查模型文件：models/bge-m3/config.json 是否存在，model.safetensors 是否完整下载
  4. 检查内存：bge-m3 ~2GB + bge-reranker-large ~2GB，总 4GB+。如果内存不足会 OOM
  5. 查日志：模型服务启动日志中的错误信息

常见错误及解决：

  • CUDA out of memory：GPU 被其他进程占用。nvidia-smi 查看占用进程，kill 或减少 batch_size
  • Model not found：模型路径错误。确认 SentenceTransformer("models/bge-m3") 路径正确
  • CUDA driver version mismatch：升级 GPU 驱动或降级 PyTorch CUDA 版本
  • CPU fallback：如果无 GPU，模型会在 CPU 上运行（慢 10x），但功能正常。配置 device="cpu"

3.4 性能问题

Q77: 【性能】RAG 端到端响应时间 8s+，用户体验差，怎么优化到 3s 以内？ 高级

延迟拆解（典型 8s 场景）：Embedding 100ms + Milvus 6次串行 300ms + Rerank 300ms + LLM 生成 4s + 幻觉校验 3s = ~8s。

优化方案（按收益排序）：

  1. LLM 流式输出（-3.5s 体感延迟）：首 token ~200ms 后用户就开始看到答案，不需要等完整生成。已实现 SSE
  2. 声明校验并行（-2s）：当前逐句串行调 LLM 裁判。改为 asyncio.gather 并行 3-5 句，省 60% 时间
  3. Milvus 并行检索（-250ms）：6 次串行改 asyncio.gather 并行
  4. FAQ 快速路径（-7s）：FAQ 命中 rerank>0.85 跳过 LLM + 校验，直接返回标准口径 ~300ms
  5. Embedding 缓存（-100ms）：高频查询 Embedding 缓存到 Redis
  6. 声明校验异步化（-3s）：答案先返回给用户，声明校验异步执行，如果校验不通过再推送 flag 事件修正

优化后预期：FAQ 快速路径 ~300ms，常规路径首 token ~500ms，完整响应 ~4-5s，校验异步后用户体感 ~1s。

Q78: 【性能】高并发下 RAG 系统响应时间急剧上升，怎么排查和解决？ 高级

排查步骤：

  1. 定位瓶颈：用 APM（如 Prometheus/Grafana）看各阶段延迟分布。是 LLM 排队、Milvus 排队还是 DB 连接池耗尽？
  2. 检查 LLM 并发：本地 qwen2.5-14b 单 GPU 同时只能处理 1-2 个请求，并发时排队。查看 GPU 利用率
  3. 检查 Milvus 并发：Milvus 单节点支持并发检索，但负载高时检索延迟上升
  4. 检查 FastAPI worker：uvicorn --workers 4，如果只有 1 个 worker 并发受限
  5. 检查 DB 连接池：连接池耗尽时 pool_timeout 等待

解决方案：

  • LLM 多实例：部署多个 LLM 服务实例，Nginx 负载均衡
  • 请求队列+限流：RAG 请求加 Redis 限流（如每用户 5 QPM），超出排队
  • FastAPI 多 worker：uvicorn --workers $(nproc) 按 CPU 核数启动
  • 异步非阻塞：确保所有 I/O 操作用 async/await，不阻塞事件循环
  • 缓存高频答案：相同问题的 RAG 答案缓存 1h，命中跳过整个管线
  • GPU 升级：更大显存支持更大 batch_size，提升 LLM 吞吐
Q79: 【性能】法规文档入库速度极慢（1万条 chunk 需要 10 分钟+），怎么优化？ 进阶

瓶颈分析：入库流程 = 解析→分块→Embedding→Milvus 写入。1 万条 chunk：

  • 解析+分块：~5s（CPU 计算）
  • Embedding：逐条调 HTTP = 100ms × 10000 = 1000s ← 主要瓶颈
  • Milvus 写入：批量 insert ~10s

优化方案：

  • 批量 Embedding：embedder.embed(texts) 支持批量。一次 64 条，1 万条只需 156 次 HTTP 调用 ~16s
  • 并行 Embedding：多批次并行调用，asyncio.gather 每批 64 条
  • Milvus 批量写入：insert_vectors() 一次写入所有向量，不分批
  • 后台任务：入库用 Celery/BackgroundTasks 异步执行，不阻塞 API 响应
  • 增量入库：只入库新增/修改的条款，不全量重建

优化后预期：批量 Embedding + 并行 = ~30s，Milvus 写入 ~10s，总计 ~50s（提升 12x）。

Q80: 【性能】前端 SSE 流式输出卡顿（token 之间延迟 1s+），怎么排查？ 进阶

排查步骤：

  1. 检查 LLM 流式：直接 curl LLM API 的 stream: true，看 token 延迟。如果 LLM 端就慢，是 GPU 性能问题
  2. 检查后端 SSE 中转：llm_client.chat_stream() 用 httpx.AsyncClient.stream()。如果 aiter_lines() 有缓冲，会攒一批再 yield
  3. 检查 FastAPI SSE：sse-starlette 是否正确配置 ping 心跳
  4. 检查前端 EventSource：浏览器 DevTools Network 面板看 EventStream 延迟
  5. 检查 Nginx/代理：如果有反向代理，需配置 proxy_buffering off 避免缓冲 SSE

解决方案：

  • httpx 流式优化：确保 client.stream() 用 aiter_bytes() 而非 aiter_lines()，避免等换行符
  • Nginx 配置：proxy_buffering off; proxy_cache off; chunked_transfer_encoding on;
  • LLM batch_size：增大 LLM 推理 batch_size，提升单位时间 token 产出
  • 前端降级：如果 SSE 卡顿严重，降级为非流式（一次性返回完整答案）

文档结构（本项目）按法规"第X条"为粒度天然支持引用溯源依赖文档格式法规/标准
语义聚合用 Embedding 聚合语义相近的句子语义最优计算量大、不可控非结构化文本
父子分块小块检索，大块送 LLM检索精+上下文全实现复杂长文档

本项目选文档结构分块的原因：① 法规天然有"第X章→第X条"结构；② 引用溯源需要——每块绑定 clause_id，答案可溯源到具体条款号；③ 512 token 上限内大部分条款一条一个 chunk。

优化方向 — 父子分块：检索时用小块（条款内句子级），但送 LLM 时扩展到父块（完整条款），保证上下文完整。如检索命中"第三十五条第二款"，送 LLM 的是完整"第三十五条"全文。

5.1 行业同类 RAG 项目

PharmaReg 的差异化优势：

  • 垂直行业深度：法规解析（中文数字转整数）、条款级分块、引用溯源、幻觉双重校验、置信度门控——这些通用 RAG 平台没有
  • 多 Agent 合规矩阵：10 个制药专家 Agent + 角色权限矩阵，通用平台通常是单 Agent 或简单路由
  • 审计完整性：哈希链审计日志 + 电子签名（21 CFR Part 11），通用平台通常只有操作日志
  • 状态机管理：偏差/变更/SAE/CAPA 状态机 + Agent 不写库约束，通用平台没有业务状态管理
  • 评估门禁：200 条评估集 + 幻觉注入测试 + CI 质量门禁，通用平台通常没有评估体系
Q91: 和 Dify/FastGPT 相比，你们有什么劣势？可以借鉴什么？ 高级

劣势：

  • 通用性差：PharmaReg 深度绑定制药合规，换到其他行业（如法律、金融）需要大量改造。Dify/FastGPT 通用性强
  • 知识库管理 UI：Dify/FastGPT 有完善的文档管理 UI（上传、解析、分块预览、调试）。PharmaReg 的知识库管理主要靠 API
  • 调试工具：Dify 有可视化 Workflow 编排和调试面板。PharmaReg 的 RAG 链路调试靠日志
  • 多格式支持：Dify 支持多种文档格式（PDF/Word/Excel/网页）。PharmaReg 主要处理纯文本法规
  • 社区生态：Dify/FastGPT 有活跃社区和插件生态。PharmaReg 是内部项目

可借鉴的优化点：

  • 知识库管理 UI：增加文档上传→解析→分块预览→入库的完整 Web UI，降低运维门槛
  • RAG 调试面板：增加可视化调试——输入问题后展示每阶段中间结果（意图分类结果、检索候选、Rerank 分数、LLM prompt/输出、校验结果）
  • 多格式解析：支持 PDF（法规原文常为 PDF）和 Word 格式，用 PyMuPDF/python-docx 解析
  • Workflow 可视化：用 LangGraph Studio 或自研可视化工具展示 Agent 路由图
  • A/B 测试：支持不同 Prompt / 模型版本的 A/B 测试对比

PharmaReg Agent 架构的独特性：

  • Agent 不写库约束：这是其他所有项目都没有的设计。在合规场景中 AI 只做建议，不做决策
  • 角色权限矩阵：基于制药行业角色分工（操作员/QA/研究者/CRA/PV/合规专员）做 Agent 可见性控制。其他项目通常不做角色级权限
  • 确定性工具调用：Agent 内部用关键词规则（如偏差分级）而非 LLM ReAct。其他项目都依赖 LLM 做工具选择
  • 服务层状态机分离：状态管理在 service 层，Agent 只做建议。其他项目通常在 Agent 内管理状态

5.3 差异化分析

Q93: 如果面试官问"你们项目和市面上的 RAG 项目最大的差异化在哪里？" 高级

三个核心差异化：

① 幻觉防护体系（最大差异化）

  • 双重校验（条款存在性 + 声明蕴含 LLM 裁判）
  • 三维度加权置信度（rerank + clause_hit + claim_pass）
  • 置信度门控 + 阻断策略（<0.6 阻断、未验证>30% 阻断）
  • Stub 模式证据门（rerank<0.45 标记人工审核）
  • 200 条评估集含 24 条幻觉注入测试，CI 门禁 100% 阻断

→ 通用 RAG 项目通常只有"检索→生成"两步，没有系统化的幻觉防护。

② 条款级引用溯源

  • 文档结构化分块（按"第X条"为粒度）
  • 每个 chunk 绑定 clause_id，答案引用可回溯到具体条款
  • build_citations 回查 MySQL 构建结构化引用
  • SSE 先推 citation 事件，用户先看到引用再读答案

→ 通用 RAG 项目通常只返回答案，不做引用溯源或只标注文档名。

③ 制药合规 Agent 矩阵

  • 10 个制药专家 Agent（偏差/变更/SAE/审计/培训等）
  • 角色权限矩阵（操作员/QA/研究者/CRA/PV/合规专员）
  • Agent 不写库约束（AI 只建议，人工决策 + 电子签名）
  • 服务层状态机管理业务生命周期

→ 通用 Agent 项目面向通用场景，没有制药行业深度。

5.4 可借鉴优化点

Q94: 从行业同类项目中，你觉得 PharmaReg 还可以借鉴哪些优化？ 高级

从 Dify 借鉴：

  • 可视化 Workflow 编排：用拖拽方式编排 RAG 链路和 Agent 流程，降低非开发人员使用门槛
  • Prompt 调试面板：在线编辑 Prompt → 实时预览 LLM 输出 → 对比效果

从 FastGPT 借鉴：

  • 分块预览：文档入库前预览分块效果，手动调整分块边界
  • 问答标注：用户对答案点赞/点踩，标注数据回流优化检索和 Prompt

从 LangChain-Chatchat 借鉴：

  • 混合检索：BM25 + 向量检索 + RRF 融合，提升专业术语检索精度
  • 父子分块：小块检索、大块送 LLM，兼顾检索精度和上下文完整

从 LangGraph 借鉴：

  • 图式工作流：偏差处理全流程建模为图，支持条件分支和人在回路
  • 状态检查点：Agent 执行中途可暂停/恢复，支持长流程

从 AutoGen 借鉴：

  • 多 Agent 协商：复杂合规问题（如"这个偏差是否需要召回"）可以多 Agent 讨论——QAAgent 检索法规 + DeviationAgent 分析偏差 + ComplianceAgent 评估合规风险

从行业最佳实践借鉴：

  • Query 意图 LLM 分类：用轻量 LLM 做意图分类，替代关键词匹配，提升路由精度
  • Self-RAG：LLM 自主判断是否需要检索、检索结果是否相关、答案是否有依据
  • Corrective RAG (CRAG)：检索质量评估→低质量检索触发 web 搜索补充
  • 多模态：支持法规文档中的表格和图片（GMP 附录常有表格）
Q95: 如果让你重新设计这个项目，你会做什么不同的技术选型？ 高级

  • bge-m3 Embedding（中文最优 + 本地部署）
  • bge-reranker-large CrossEncoder（精度最高）
  • FastAPI + React 全栈（异步 + 类型安全）
